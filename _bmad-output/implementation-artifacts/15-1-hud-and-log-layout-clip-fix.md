# Story 15.1: HUD and Log Layout Clip Fix

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a player,
I want to see the whole HUD and the newest combat log lines at any window size,
so that the information the game is already producing actually reaches me.

## Context & Why This Story Exists

Epic 15 ("Playtest Response") is the **third pre-ship playtest-response epic** (the Epic-13/14 pattern), added 2026-07-24 after a post-Epic-14 agent-driven desktop playtest confirmed the loop is **completable end-to-end for the first time** and all five 2026-07-16 Blockers are fixed — but surfaced **20 new findings** (record `playtest-sessions/agent-playtest-2026-07-20.md`; triage `playtest-sessions/agent-playtest-2026-07-20-triage.md`; `sprint-change-proposal-2026-07-24.md`). Story 15.1 is **Band 1 — the readability hotfix — and it lands FIRST and ALONE** (proposal §3.1; the triage: "Land first and alone"). It is the single highest-leverage fix in the epic: it un-hides most of the HUD/log that Epic 14 actually shipped but that a layout bug renders invisible, and it is what makes the ≥5-session on-device human playtest (the standing OSG-1 obligation) genuinely worth running.

It closes findings **F1** and **F2** (`agent-playtest-2026-07-20.md` lines 96–110; `agent-playtest-2026-07-20-triage.md` line 31; proposal §4.1 Band-1 row):

> **F1 — One layout bug hides nearly the entire HUD.** The HUD label column — HP "N/18", gold, bag, node counter, class line, affinity badge, the highlight legend — renders clipped at the window's left edge (the report reads it as a negative-x offset), at **every size tested (574/774/984 wide; portrait, landscape, tall)**. The same root cause clips the first ~2 characters of every log line. **Most of Epic 14's HUD work is shipped and invisible.**
> **F2 — The event log shows a stale 3-line window; the newest lines are the hidden ones.** The log's one feedback channel presents the past as if it were the present — new lines overflow invisibly below the visible window while stale lines stay on screen.

**This story is PRESENTATION-ONLY over shipped, pinned view-model/layout contracts. It makes NO domain / command / event / RNG / save change and re-pins NOTHING.** It is the same ratified presentation shape as the Band-2 Epic-14 stories (14-8…14-11): the assertable layout DECISIONS live on the scene-free `RefCounted` `TacticalLayoutProfile` seam with a unit test; the `Control` presenter is thin glue verified by construction + the `test_run_flow_scenes_load.gd` compile guardrail. **Every seed-regression fingerprint stays byte-identical across all of Epic 15** (proposal §2.1; epics.md Epic-15 sequencing note). The four ratified Epic-15 design decisions do **NOT** touch this story: **D1 HP-persistence → 15.5, D4 shards-on-death → 15.5, D2 move-confirm → 15.7, D3 class-weighted rewards → 15.6.** Do not pull any of them in.

### ⭐ THE CRUX — 15.1 is a SHARED-ROOT-CAUSE layout fix on the `TacticalLayoutProfile` seam; it lands ALONE and fixes ONLY the HUD/log clip (read before Task 1)

Four boundaries define this story. Get them wrong and you either over-reach into the other 11 Epic-15 stories or ship a cosmetic band-aid instead of the root fix:

1. **The root cause is STRUCTURAL and shared — fix the region plan, do NOT nudge label offsets.** AC1 is explicit: "the fix addresses the shared layout root cause in the presenter rather than nudging individual label offsets," and AC3 pins "the layout decisions stay on the pinned `TacticalLayoutProfile` seam (verified without a SceneTree)." The confirmed structural cause (see "The load-bearing architecture reality" below): the semantic region plan gives the **`status` region exactly ONE ~7%-of-height control band** while the Epic-14 HUD stacks **nine Labels + a ProgressBar** into it, and gives the **`log_or_outcome` region ZERO size on both phone profiles** and only ~44px (2–3 lines) on desktop/tablet — so the shipped content overflows and `clip_contents` hides it. The DECISION about how much reachable space the HUD and log get, and whether the log region exists on phone profiles, belongs on the `TacticalLayoutProfile` seam with a unit test. The presenter renders the shipped HUD/log to FIT that space (wrap / scroll / tail), it does not hand-offset labels.

2. **Lands FIRST and ALONE — it is NOT the other 11 Epic-15 stories.** 15.1 fixes the HUD/log **clip** only. It does **NOT**: correct attack-preview damage (15.2), add threat telegraphs (15.3), add quit/resume (15.4), wire the event-node/run-summary economy or HP persistence (15.5), fix the reward modal or class-weight the pool (15.6), add mis-tap/move-confirm safety (15.7), animate movement/deaths/transitions (15.8/15.9), collapse gray slabs / re-craft hero-select / disambiguate hazard-vs-corpse art (15.10, that is where F17/F19/F11 live), pass over player-facing copy / kill snake_case leaks (15.11), or add the weapon/kit line (15.12). If you find a leaked `enemy_3` id or an empty gray slab while you are in the presenter, **leave it** — it is another story's finding. Your surface is the HUD column being on-canvas and the log showing its live tail.

3. **The fix rides the EXISTING resize path — event-driven, NEVER a `_process` poll.** 14-11 already gave `tactical_board_presenter.gd` an event-driven `viewport.size_changed` → coalesced `_apply_resize()` → `_relayout_regions()` + `render()` handler (the F15 fix). The "resize mid-fight" clause of AC1 flows through that existing path for free once the region plan and HUD/log rendering are fixed — a resize re-reads the profile and re-lays the regions. **Do NOT add a `_process`/`_physics_process` poll** (project-context.md: "Avoid per-frame work in nodes that can update through events, signals, or explicit refresh calls"; the ratified 14-3 "one draw pass per render" rule). Do NOT rebuild the resize handler; extend the region plan it already drives.

4. **Changing the region plan WILL fail the layout-profile test — that is EXPECTED; update its pinned expectations deliberately.** `godot/tests/unit/ui/test_tactical_layout_profiles.gd` pins the region math for each profile (`_assert_primary_controls_reachable_inside_content`, `_board_is_largest_region`, "every region inside content", the exact top-level `to_dictionary()` key set). When you re-shape the region plan, these assertions re-evaluate and some will trip. **This is the same discipline as a fixture re-pin: update the pinned expectations in the SAME change, with the new region plan as the justification — never silence a drift.** Register the new expectation the fix creates (e.g. the `log_or_outcome` region is reachable/non-empty on the profiles where you now surface the log; the HUD region holds its content without overflow). Two invariants the test enforces that your fix MUST preserve: **the board stays the largest region** (`_board_is_largest_region`) and **every region stays inside the content area**. Reallocate space to the HUD/log without ever making a control band the largest region — which is exactly why a **scroll affordance** is often the right lever rather than an unbounded band grow.

### The load-bearing architecture reality (read before Task 1)

The live combat surface is **`godot/scripts/ui/presenters/tactical_board_presenter.gd`** (the `Control` scene-root script of `godot/scenes/game/tactical_board.tscn`). This is the **correct file** — the 14-1 retro flagged that stories mis-named `gameplay_shell_presenter.gd`/`tactical_board_grid.gd`; the live board surface is `tactical_board_presenter.gd`, and `tactical_board_grid.gd` is only the thin op-list DRAW Control. The semantic layout DECISION lives in the scene-free `RefCounted` **`godot/scripts/ui/view_models/tactical_layout_profile.gd`** (`TacticalLayoutProfile`).

**The confirmed structural root cause (grep-verified against source — this is F1 + F2):**

- **The presenter builds one `Panel` per region + a `PRESET_FULL_RECT` `Label`, positioned entirely by the profile's region rects.** `_build_regions()` (lines 336–364) creates a `Panel` at `rect.x/y`, size `rect.w/h` for each of the six regions (`board`, `preview`, `confirm_cancel`, `inspect`, `status`, `log_or_outcome`), with a `PRESET_FULL_RECT` content `Label`. `_relayout_regions()` (lines 319–331) re-flows those panels on resize. The panels get their geometry from `TacticalLayoutProfile.to_dictionary().regions`.
- **The `status` region is ONE control band (~7% of height), but the HUD stacks NINE Labels + a ProgressBar into it.** In `TacticalLayoutProfile._build_stacked_layout()` (lines 168–202) `status` gets `control_height = maxf(44, area.size.y * 0.07)` — one of four equal control bands beneath the board. `_build_hud_controls()` (presenter lines 959–995) builds `_hud_box` (a `VBoxContainer`, `PRESET_FULL_RECT`, `theme_type_variation = HudBox`) containing the turn label, HP label, HP `ProgressBar`, gold, bag, node, class, affinity, and legend labels — **nine labels + a bar in a ~44–60px band.** The host `Panel` is set `clip_contents = true` (line 965), so the overflow is clipped, not shown. That is the HUD half of F1.
- **The `log_or_outcome` region is ZERO-SIZE on BOTH phone profiles and only ~44px on desktop/tablet.** `_build_stacked_layout()` only reserves a log strip when `_profile_id == PROFILE_DESKTOP or PROFILE_TABLET` (`log_height = maxf(44, area.size.y * 0.06)`, lines 176–177); otherwise `_regions["log_or_outcome"] = _empty_rect()` (0×0, lines 199–202). `_build_side_rail_layout()` (phone landscape, lines 207–228) sets `log_or_outcome = _empty_rect()` unconditionally. **On the tested window sizes (574/774/984 wide) the profile resolves to phone_portrait / phone_landscape / tablet** (`_profile_id_for`, lines 119–128; none is ≥1280 so none is desktop) — so the log is invisible on phone profiles and a top-clipped 2–3-line strip on tablet. That is the structural F2.
- **F2's "stale head, not live tail" is a render-alignment bug, not a data bug.** The log VIEW is already correct: `TacticalCombatLogView.from_board_vm()` (`godot/scripts/ui/view_models/tactical_combat_log_view.gd`) tail-limits to the newest `MAX_LINES == 8` (newest last, line 37, 43–61). The presenter joins them with `"\n"` into the log Label (`_log_text`, lines 684–691) which is **top-aligned** in the tiny/absent panel — so the OLDEST of the rendered tail sits at the visible top and the NEWEST overflow below the clip. The fix is to make the newest lines the visible ones (a bottom-anchored / bottom-scrolled tail, and/or fit the line count to the region), plus give the log a region that actually exists.
- **F1's horizontal "negative-x" symptom is a rendering artifact on the starved/framed bands — reproduce it, it is NOT in the profile math.** The profile emits every region at `x = area.position.x` (0 for the default full content area) with full width (stacked) or a positive `rail_x` (side rail) — it never produces a negative-x rect. So the left-edge clip is a presenter/theme artifact on the short bands. Candidates to check at runtime: (a) the 14-11 **`panel_frame` nine-patch StyleBox draws a 24px border 1:1 in control pixels with no downscale** (`tools/build_sealsworn_theme.gd` `PANEL_MARGIN == 24`; project-context.md §Epic-14 nine-patch gotcha) — on a ~44px band the frame borders dominate the control and combine with `clip_contents` to swallow content; (b) the **compact single-line HUD fallback** (`_compact_hud_text`, lines 567–577) is one long left-aligned line that overflows a narrow (side-rail ~32%) region; (c) a container anchor in the presenter. **Read `godot/assets/ui/sealsworn_theme.tres` + `tools/build_sealsworn_theme.gd` and reproduce at 574/774/984 (portrait + landscape + a mid-fight resize) before choosing the fix.**
- **The HUD already has a reachability-degrade path — but it is INSUFFICIENT, which is the whole point of this story.** `_render_hud()` (lines 501–518) shows the full `_hud_box` only when `_status_slot_reachable(layout)` (≥44px, inside content; lines 523–526) and otherwise degrades to the compact single-line fallback. Neither branch actually fits nine HUD elements legibly into a one-band region — the fix has to give the HUD real, reachable space and/or make it scroll, not lean harder on the compact fallback.
- **The board fit already re-scales; leave it alone except for the space it yields to the HUD/log.** `_render_board_grid()` fits the grid via `TacticalBoardGridFit.from_region(...)` from `_board_region_size(layout)` (presenter ~lines 1197–1248). If you grow the HUD/log bands, the board region shrinks — the board must **stay the largest region** (`test_tactical_layout_profiles.gd::_board_is_largest_region`). Do not touch `TacticalBoardGridFit`.
